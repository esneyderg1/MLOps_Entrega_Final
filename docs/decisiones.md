| 2026-09-18 | **EDA completado** (`notebooks/01_eda.ipynb`): no eliminar duplicados exactos (esperables por baja cardinalidad combinada + salarios redondeados; no cruzan entre años) ni atípicos altos (1.98%, roles senior/ejecutivos reales); agrupar `job_title` y `employee_residence`/`company_location` por baja frecuencia en el preprocesamiento; evaluar `log1p(salary_in_usd)` como variante de target (destransformando con `expm1` antes del RMSE); partición temporal confirmada: train `work_year`≤2024 (62.234 filas), validación `work_year`=2025 (15.875 filas) | Distribuciones de target y de `experience_level` consistentes entre 2024 y 2025 (ver notebook); cero nulos en el dataset, no se requieren imputaciones | Equipo |

| 2026-09-19 | Lógica de descarga y metadata en `src/proyecto_final/data/acquisition.py` (funciones puras, testeadas con `pytest` sin red real); el flow en `src/proyecto_final/flows/acquisition_flow.py` solo orquesta y agrega reintentos (`retries=3`) en la task de descarga | Separar lógica de orquestación (regla 3 de CLAUDE.md): permite testear la adquisición sin levantar Prefect y reutilizar las funciones si se necesitan en otro lado | Equipo |
| 2026-09-19 | **Servidor de Prefect: el equipo trabaja en Prefect Cloud, con código agnóstico al servidor.** Los flows NUNCA referencian URLs ni API keys de Prefect; la conexión sale del perfil local de cada máquina (`prefect cloud login` para Cloud, o un perfil sin API URL para modo local/efímero). Cada integrante elige cómo verlo; el peer review puede ejecutar todo en local sin configurar nada | Dashboard compartido para el equipo sin acoplar el repo a credenciales (que nunca se commitean); el mismo código corre en Cloud, server local o modo efímero | Equipo |
| 2026-09-19 | **Procesamiento (actividad 5):** partición temporal ANTES de cualquier transformación que "aprenda" de los datos; las categorías frecuentes de `job_title`/`employee_residence`/`company_location` se calculan solo con train (`min_freq: 0.01` en `configs/config.yaml`) y lo raro/no visto cae en `OTHER`; `remote_ratio` se trata como categórica; el preprocesador sklearn usa OneHotEncoder(`handle_unknown="ignore"`) para tolerar categorías nuevas en producción | Evitar leakage temporal; con 1% de umbral quedan 15 `job_title` + `OTHER` (de 312) y 3 países + `OTHER` (~90% de registros son de EE. UU., limitación ya documentada en `docs/dataset.md`); el umbral es configurable si el baseline sugiere afinarlo | Equipo |
| 2026-09-19 | **Baseline (actividad 6):** dos runs en MLflow — `dummy_median` (RMSE 78.233 USD) y `rf_baseline` (RandomForest n_estimators=100, max_depth=10: **RMSE 68.547 USD**, MAE 48.527, R² 0.225). El RMSE del `rf_baseline` es el piso a superar por Optuna (criterio de éxito: mejorar ~10%, ver `docs/dataset.md`). El pipeline completo (preprocesador + modelo) queda logueado en cada run | El dummy da el piso "sin modelo": el RF ya lo mejora 12,4%, confirmando que las features aportan. R² moderado esperado (features categóricas gruesas, documentado como riesgo en `docs/dataset.md`) | Equipo |
| 2026-09-19 | Fix multiplataforma: `enable_utf8_output()` en `config.py`, llamada al inicio de los flows que usan MLflow | MLflow imprime emojis al cerrar runs y la consola cp1252 de Windows lanza `UnicodeEncodeError` rompiendo el task de Prefect | Equipo |
| 2026-09-20 | **Optimización (actividad 7):** estudio de Optuna sobre el mismo RandomForest del baseline — 15 trials, espacio de búsqueda propio en `configs/config.yaml` (`n_estimators`, `max_depth`, `min_samples_split`, `min_samples_leaf`, `max_features`). Un parent run (`rf-optuna-salarios`) + 15 child runs (`nested=True`), cada uno con su pipeline completo logueado. Mejor resultado: **RMSE 68.142 USD** (`n_estimators=125, max_depth=28, min_samples_split=11, min_samples_leaf=2, max_features=log2`) | Generalizar `build_baseline_pipeline` en `build_rf_pipeline(**rf_params)` evita quemar cada hiperparámetro como argumento propio y lo reutilizan tanto el baseline como Optuna | Equipo |
| 2026-09-20 | **Hallazgo honesto: Optuna solo mejora el baseline en 0.59%** (68.142 vs 68.547 USD), muy por debajo del ~10% fijado como criterio de éxito en `docs/dataset.md`. **No se reabre la actividad 7** para forzar el número: el techo de desempeño parece estar en las features (categóricas gruesas, dataset con 90% EE. UU.), no en los hiperparámetros del RandomForest | Evita ampliar indefinidamente el espacio de búsqueda para "maquillar" una métrica sin sustento; se documenta como limitación real del enfoque actual, a discutir en la actividad 8 (¿vale la pena probar otra familia de modelos antes de fijar el candidato?) | Equipo |
